# After the P0 release: make the supported experience effortless

Reviewed 2026-10-02 against the implemented provider, Google, durable-task and
first-result packages. This is a source and integration review, not a measured
usability comparison with other products.

## What changed

- Tool-capable providers now share Conch-owned tools and approvals. ChatGPT
  subscriptions use the supported Codex device sign-in and isolated credentials.
  Capability checks expose unavailable tools before a starter job runs.
- Gmail and Calendar connect directly to Conch with selected account identity,
  incremental access, reconnect and exact draft review. Drafts are never sent by
  this connector. Optional Drive access is metadata-only, not document ingestion.
- Tasks persist authorized scope, write-ahead operations and independently checked
  receipts. They resume in the original conversation, reconcile uncertain writes,
  preserve deduplication across deletion/restore, and separate an unverified model
  result from verified completion.
- Onboarding starts with a document brief, daily briefing or follow-up drafts.
  Personalization follows useful work. Results and interrupted work survive reload.

The architectural improvement is that a provider no longer owns the meaning of
the job. Conch owns the accounts, tools, approvals, progress and saved-result proof.
This does not make a chat-only model tool-capable or prove a model-written report
factually correct. Those boundaries are visible rather than concealed.

## Next, in order

### 1. Run the real-account acceptance matrix

Deterministic tests exercise the adapters and interruption paths; the actual Codex
startup smoke test deliberately used no account and no inference. Google consent
and authenticated model output still need authorized live acceptance.

Run the three recipes on each supported provider with a dedicated test mailbox
and calendar. Cover the remote callback, partial consent, expired access, Stop
during refresh, restart before/after a draft write, and same-account reconnect.
Inspect saved documents and Gmail account, thread, recipients, body and draft ID.

**Pass condition:** no sends, no duplicate drafts, no false completion states,
and equivalent review/recovery behavior across supported providers. Record task
success, time to result, user decisions and failure recovery separately from
model answer quality. Do not label untested provider/model combinations supported.

### 2. Remove Google Cloud Console from the consumer journey

The direct connector is implemented, but a self-hosted installation currently
requires operator-owned OAuth registration. That is workable for a developer;
it is not the final consumer experience.

Choose the distribution model before building a generic OAuth broker: a managed
Conch service, a supported native application, or deliberately operator-managed
self-hosting have different redirect, secret and verification requirements.
Complete the actual Google registration and verification work for the chosen
model. Keep the self-hosted setup as an advanced route.

**Pass condition:** an intended consumer installs the supported distribution,
chooses their personal or work account, grants understandable access and finishes
a useful job without project IDs, redirect-URI editing or unexplained console
steps. Reconnect remains inside the interrupted job.

### 3. Put repeatable jobs and attention on Home

The starter recipes currently live in onboarding. The primary navigation still
leads with chat and exposes separate tasks, routines and integrations.

Promote the existing recipes to reusable actions rather than creating another
automation subsystem. Home should show **Needs you**, **Working**, and **Ready**,
alongside recent results and a few familiar jobs. A successful job can become
**Do this again**, then **Do this every Friday**, with its account and scope shown.

**Pass condition:** a person can repeat a briefing for another date, find a pending
draft approval, reconnect, resume and inspect the result without learning internal
task or integration terminology. Navigation and reload never start work twice.

### 4. Ship immutable stable releases

The installers and updater still build from source, with the installers defaulting
to moving `main`. CI exists; consumer release artifacts and stable-channel
promotion are not yet a complete distribution pipeline.

Create versioned, integrity-checked artifacts and an explicit Stable/Preview split.
Stage updates away from the running installation, verify startup, and document
rollback alongside data-format compatibility. Preserve the source installer for
contributors and advanced self-hosting.

**Pass condition:** a clean supported machine installs and updates without compiler
diagnostics or source-build knowledge. A failed startup restores a working version
without losing accounts, conversations or effect receipts.

### 5. Broaden document input after the narrow flow is measured

The first document job deliberately accepts TXT, Markdown and CSV, at most 48 KB
before applying a 12,000-character limit. Drive access lists metadata only.

Reuse maintained parsers for PDF and DOCX, then add explicitly selected Drive
document content. Retain source attribution, account identity, extraction errors
and clear limits. Keep untrusted document instructions separate from job authority.

**Pass condition:** common real documents produce inspectable extracted sources
and useful editable deliverables; encrypted, corrupt, scanned or oversized inputs
receive a specific recovery path rather than silent truncation or invented facts.

## What to defer

More providers, more channels, a large skill marketplace and elaborate agent
controls should wait until the live acceptance matrix and repeat-job experience
are dependable. The next advantage is less setup, supervision and repair per
successful job, not a longer feature list.
